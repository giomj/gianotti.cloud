# Enterprise Briefing — Why RSA Is Already Obsolete

**Prepared by:** CBJG Holdings LLC · Quantum Security Advisory
**Audience:** Board of Directors, CISO, Chief Architect, PKI operations
**Classification:** Public — customer-facing advisory

## 1. The bottom line

Every RSA-protected asset your organisation owns has **two independent risk timelines**:

1. **Classical risk — happening today.** Real deployed RSA falls to well-understood classical attacks whenever key generation, padding, exponent choice, or PKI hygiene is imperfect. Every attack in `rsa_classical_attacks.py` has been used against production systems in the last decade.
2. **Quantum risk — deterministic, not hypothetical.** Shor's algorithm mathematically breaks RSA in polynomial time on a fault-tolerant quantum computer. The only unknown is *when* such a machine is fielded — NSA planning documents (CNSA 2.0) assume the window closes between 2030 and 2035, and the NIST PQC standards (FIPS 203 / 204 / 205) were finalised in August 2024 precisely to give industry a viable migration target ([NIST, 2024](https://www.nist.gov/news-events/news/2024/08/nist-releases-first-3-finalized-post-quantum-encryption-standards)).

The "Harvest Now, Decrypt Later" (HNDL) attack pattern eliminates the option of waiting. An adversary that records your traffic today decrypts it retroactively the moment a Cryptographically Relevant Quantum Computer (CRQC) is available. **Any data with a confidentiality horizon longer than 5–10 years is already compromised** unless it is being transmitted under a PQC-hybrid channel.

## 2. Attack-to-mitigation mapping

| # | Attack class | Present-day exploit example | Cryptographic root cause | Enterprise mitigation |
|---|---|---|---|---|
| 1 | **Shor / quantum factoring** | Any archived RSA-encrypted capture, retroactively | Integer factorisation is polynomial on a CRQC | **ML-KEM-1024** (FIPS 203) for KEX; **ML-DSA-87** (FIPS 204) for signatures. Hybrid TLS 1.3 (X25519 + ML-KEM-768) available in OpenSSL 3.4, BoringSSL, and Cloudflare's edge today. |
| 2 | **Fermat factorisation** | 2022 discovery of FIPS-certified TLS certs with p, q only bits apart (bad hardware RNG) | Close primes: N = a² − b² factors in O((p−q)/2) | FIPS 140-3 validated keygen; third-party prime-distance audit. |
| 3 | **Pollard rho / ROCA-class** | 2017 ROCA (CVE-2017-15361) broke ~1 billion Infineon-generated keys — Estonian national ID cards, TPMs, YubiKeys | Structured/low-entropy primes | Rotate keys generated by affected libraries; enforce HSM-based keygen with independent entropy source. |
| 4 | **Wiener low-d attack** | Repeatedly found in embedded / IoT devices that shrank d for signing performance | d < N^0.25 / 3 recoverable by continued fractions | Never optimise by shrinking d; use CRT-RSA or migrate signing to Ed25519 / **ML-DSA-65**. |
| 5 | **Common-modulus attack** | Duplicate N across certificates issued by mismanaged internal CAs | Reused N with distinct e | PKI scan for duplicate moduli; automated cert lifecycle (ACME / cert-manager); unique-N policy enforced at issuance. |
| 6 | **Bleichenbacher / ROBOT** | 2017 ROBOT attack against F5, Citrix, Cisco, Bouncy Castle TLS stacks | PKCS#1 v1.5 padding oracle | Deploy RSA-OAEP for encryption, or eliminate RSA KEX entirely by moving to **ML-KEM** hybrid ciphersuites in TLS 1.3. |
| 7 | **Coppersmith / Håstad broadcast** | Small-e public keys with partial known plaintext | Low e (typically e=3) plus short messages | Use e = 65537 with full-length OAEP-padded plaintexts; better, migrate to ML-KEM. |
| 8 | **Timing / power side-channel** | Cachebleed, TPM-Fail, LadderLeak, Minerva — extract d from non-constant-time modular exponentiation | Implementation leaks, not algorithm | Constant-time libraries (libsodium, ring, BoringSSL); HSM offload; hardware countermeasures per FIPS 140-3 Level 3+. |
| 9 | **HNDL — Harvest Now, Decrypt Later** | Nation-state pipes recording VPN, TLS, SSH, IPsec traffic *today* | Data has long confidentiality horizon; CRQC arrival is a matter of time | Begin hybrid PQC KEX immediately for anything covering >5 years of confidentiality. This is why CNSA 2.0 mandates ML-KEM-1024 for new NSS systems from 2025. |

## 3. What NIST and NSA actually require

- **FIPS 203 (ML-KEM):** replaces RSA and ECDH for key establishment. Parameter sets: ML-KEM-512 / 768 / 1024. Enterprise default: **ML-KEM-768** (NIST Category 3). CNSA 2.0 requires **ML-KEM-1024** for all national-security systems ([NSA CNSA 2.0 FAQ](https://media.defense.gov/2022/Sep/07/2003071836/-1/-1/0/CSI_CNSA_2.0_FAQ_.PDF)).
- **FIPS 204 (ML-DSA):** replaces RSA-PSS, ECDSA, and EdDSA for digital signatures. Enterprise default: **ML-DSA-65**. CNSA 2.0 requires **ML-DSA-87** for national-security use.
- **FIPS 205 (SLH-DSA):** stateless hash-based signatures — conservative backup for firmware, code signing, and long-lived root CAs.
- **CNSA 2.0 timeline:** new systems from 2025; VPN products by 2026; exclusive use by 2030–2033 depending on system class ([postquantum.com summary](https://postquantum.com/cnsa-2-0/complete-guide/)).

## 4. Migration roadmap — 12 months of concrete work

| Phase | Duration | Deliverable |
|---|---|---|
| **Discover** | 0–3 mo | Cryptographic inventory: every place RSA, ECDH, ECDSA is used — TLS endpoints, code-signing certs, VPN concentrators, HSMs, cloud KMS, database TDE, backups, IoT firmware, S/MIME, PGP. Build a Crypto Bill of Materials (CBOM). |
| **Prioritise** | 2–4 mo | Score assets by (confidentiality horizon × HNDL exposure). Anything with >10-year horizon on a public network moves to top of the queue. |
| **Pilot hybrid** | 4–8 mo | Enable X25519 + ML-KEM-768 hybrid TLS on non-critical services. Validate performance, cert chain size, client compatibility. |
| **Sign with ML-DSA** | 6–10 mo | Issue an ML-DSA-65 subordinate CA under an existing root; dual-sign artefacts. Use for code signing and internal PKI first. |
| **Cut over** | 9–12 mo | Retire RSA KEX on high-value channels; retain hybrid mode for compatibility. Update HSM firmware for FIPS 203/204 support (available in Thales, Entrust, YubiHSM roadmaps). |

## 5. What this repository proves

Running `shor_rsa_ibmq.py` on IBM Quantum hardware and observing a real machine factor N = 15 is not a curiosity. It is a live demonstration that **the mathematical primitive at the base of the internet's trust model executes on production quantum hardware today.** The remaining engineering gap between N = 15 and N = RSA-2048 is quantitative, not qualitative — qubit count, coherence time, and error-correction overhead. Every one of those numbers has been improving year-over-year for a decade.

Running `rsa_classical_attacks.py` reminds the reader that RSA is already under continuous attack from the classical side, and that the mitigations for both classical and quantum risk converge on the same answer: **migrate to NIST-standardised post-quantum cryptography now, in hybrid mode, at your own pace — before you are forced to do it under incident-response conditions.**
